# 踩过的坑

按「现象 → 根因 → 修法」记。每条都真踩过，不是预防性建议。
下次遇到相似症状先扫一遍这张表。

---

## 一、引脚相关

### 1. 拿 GPIO43/44 当普通 IO，串口直接失声

**现象**：固件烧进去后串口一个字节都不输出；再烧录报
`A fatal error occurred: TX path seems to be down`。

**根因**：`GPIO43` / `GPIO44` 是板载 UART0 的 TXD0 / RXD0，物理连到 CH343。
一旦 `pinMode()` 把它切成输入，UART0 就没有引脚可用了 —— 日志和烧录同时废掉。

**修法**：候选引脚表里剔除 43/44。烧录失败时先**拔掉所有杜邦线**再试，
能烧进去就说明是接线占了串口脚。

**教训**：探测脚本的候选表必须显式排除调试口，不能"全脚扫一遍"。

---

### 2. 一个引脚上跑两种外设，切换不是免费

**现象**：先 `PROBE`（电平探测）再 `BUSC`（I²C 扫描），扫描零命中，
看起来像屏掉了或总线坏了。日志却是：

```
[PROBE] 被拉高的脚 (4): GPIO17 GPIO18 GPIO41 GPIO42
[BUSC]  零命中: 总线被拉死 / 模块没供电 / SDA-SCL 接反   ← 假的
```

**根因**：OLED 的 SDA/SCL 在 `GPIO41/42`。`PROBE` 为了测电平，把这两个脚
`pinMode(p, INPUT_PULLDOWN)` 来回切了一遍，**`Wire.begin()` 当初做的 I²C 引脚复用被顶掉了**。
之后 `Wire.beginTransmission()` 是对着两个普通输入脚发数据，自然全零命中。

**修法**：凡是动过这两个脚的操作（`probePins` / `scanAll` / `hunt` / `listenPin` /
`syncTry` / `BRIDGE` 退出），结尾统一调 `oledReinit()`；`busCheck()` 内部也强制
`Wire.end()` → `Wire.begin(41, 42)` 重挂一次。

**教训**：**改引脚模式的人和用引脚的人不在同一处代码时，这种 bug 会以"硬件故障"的面目出现。**
看到"昨天还好今天坏了"且中间跑过探测，先怀疑引脚复用。

---

### 3. `ut_gpio read` 读外设脚恒为 0，差点误判"没接线"

**现象**：`ut_gpio read 9` 返回 0，据此判断 IO9 没接东西。

**根因**：引脚被 pinmux 成外设功能后（IO9 当时是 UART1_TX，正在通信），
GPIO 输入通路不再反映真实电平，**一律返回 0**。

**修法**：不用 `ut_gpio read` 判断外设脚的电平。改用「发协议命令看回应」，
或者临时把脚切回 GPIO 模式再读。

**教训**：之前基于该命令得出的「IO17/IO2 读 0 说明没接线」结论**全部作废**。

## 二、ECW6700 / CLI 相关

### 4. `ut_uart read` 会把 CLI 线程锁死，只能物理复位

**现象**：执行 `ut_uart read 0 16` 后，CLI 再无任何响应。`reboot`、Ctrl+C 全部无效，
只能断电重启。

**根因**：该子命令在 cmd 线程里阻塞等数据，而传入的接收缓冲是空的 —— 永久等待。

**修法**：**禁用 `ut_uart read` 做探测**。要看回传就读 `0x20204034`（LSR）判断 RDR 位，
再读 `0x20204020`（RBR）。

**教训**：嵌入式 CLI 的阻塞型读命令是雷区，试之前先想清楚有没有超时。

---

### 5. `ut_uart write` 发不了任意字节

**现象**：`ut_uart write [num] [len]` 语法看着像能发任意数据，实际发出去的永远是内部固定缓冲区。

**根因**：这个命令只操作预置 buffer，不接受用户数据。

**修法**：绕到寄存器层，直接写 THR：`write 0x20204020 0x41`。
配合 LSR 的 THRE 位做流控，实测 8 ms/字节。

**教训**：SYN6288 这类需要精确帧的协议，用 CLI 根本测不了 —— 只能自己写固件或走寄存器。

---

### 6. ECW 的命令必须以 `\r` 结尾

**现象**：发 `help\r\n` 无响应，发 `help\r` 正常。

**根因**：它的行解析只认 `\r`，`\r\n` 里的 `\n` 会被当成下一行的开始或干脆不触发。

**修法**：所有发给 ECW 的命令统一用 `\r` 结尾。桥接透传时注意别让终端自作聪明补 `\n`。

---

### 7. `isp` 同步进不去下载模式

**现象**：COM3 连续发 `0xA5` 25 秒，零响应。`eswin_tool` 也没有 devices / 读 Flash / dry-run 子命令。

**根因**：`eswin_tool` 的做法是"复位瞬间以 2 Mbps 连续发 0xA5"，时序窗口很窄；
另外缺少备份和试运行能力，误烧会覆盖出厂 CLI 且不可回滚。

**修法**：**放弃下载模式路线**，改走 WiFi OTA（见 `hardware-facts.md` 的 OTA 通道）。
这条路不需要进 bootrom，风险低得多。

---

## 三、Arduino / 工具链相关

### 8. 自动生成的函数原型把结构体挤到定义之前

**现象**：`struct Th` 明明写在文件里，编译报 `'Th' does not name a type`。

**根因**：Arduino 会在编译前自动生成函数原型并插到文件最前面。
如果结构体定义在文件中部，原型里用到它的函数就会先于定义出现。

**修法**：**结构体、全局对象一律放文件最前面**，在第一个函数之前。

---

### 9. `Serial1.begin()` 不返回 `bool`

**现象**：`if (!Serial1.begin(...))` 编译不过，或永远判为成功。

**根因**：本版 Arduino-ESP32（3.3.12）里 `HardwareSerial::begin()` 返回 `void`。

**修法**：不判返回值，改用"发一帧看有没有回包"来验证 UART 是否真正工作。

---

### 10. `make_ota_aa.sh` 结尾的 `rm -rf` 被安全策略拦掉

**现象**：脚本 exit=1，但编译产物其实已经生成好了。

**根因**：脚本末尾的清理步骤调 `rm -rf` 被沙箱拦了，导致整体退出码非零。

**修法**：手动调 `otatool.exe` 补最后一步打包，别依赖脚本的整体成功标志。

**教训**：自动化脚本的退出码 ≠ 实际结果，尤其末尾有清理动作时。

---

## 四、硬件接线相关

### 11. 排针没焊，看着"接了"其实零连接

**现象**：ESP32-S3 模组板平躺在面包板上，飞线插得好好的，软件怎么测都是全零命中。
内部上拉读 1、下拉读 0（完全悬空的特征）。

**根因**：模组板出厂常是裸板，只有镀金过孔，**排针根本没焊**。

**修法**：焊排针。判据是"引脚完全悬空"——软件层面和"线没接"完全无法区分。

**教训**：**软件测不出来的，往往是眼睛一秒钟能看出来的。** 排查到最后一步该拍照看实物。

---

### 12. I²C 接反不是花屏，是全黑

**现象**：`SDA=42 / SCL=41` 接了，屏没任何反应，扫描零命中。

**根因**：这块 SSD1306 模块的方向是固定的。对调 SDA/SCL 后从设备根本不会应答。

**修法**：`SDA=GPIO41` / `SCL=GPIO42`。判据是扫描结果，不是画面 —— 接反时**没有画面可看**。

---

### 13. 模块没板载上拉

**现象**：接线完全正确，扫描仍然零命中。

**根因**：少数廉价 I²C 模块省掉了那两颗 10k 上拉。

**修法**：开内部上拉（`Wire.begin()` 默认就开）。
判据：设成内部下拉还读 HIGH → 有外部上拉；读 LOW → 没有，靠内部上拉也能跑但要降速。

---

## 五、方法类

### 14. 「电气级探测」比「协议探测」便宜得多

`PULLUP` / `PROBE` 这类命令做的是：把脚设成「输入 + 内部下拉」，读电平。
外部模块的上拉电阻（4.7k~10k）远强于内部下拉（约 45k），所以**真正接在模块上的脚会读 HIGH**。

好处：不需要知道地址、不需要对方答应答、不需要协议正确 —— **只要对方有电就能测出来**。
这个手段在"总线上有器件但地址不对"和"线插错位置"两种情况下都能直接定位。

配套的对照点：`GPIO0`（BOOT，板载 10k 上拉）必须读 HIGH。
**如果连它都读不出来，说明是探测方法本身失效，前面所有结论都不可信。**

### 15. 先证伪最便宜的假设

按成本从低到高排：

| 顺序 | 方法 | 能排除什么 |
| --- | --- | --- |
| 1 | 读启动日志 | 板子死没死、有没有供电 |
| 2 | 总线扫描 | 器件在不在 |
| 3 | 内部上拉/下拉分别读电平 | 线悬空、被拉高、还是被拉低 |
| 4 | 全板扫"谁有外部上拉" | SDA/SCL 到底接在哪个脚 |
| 5 | 对调 SDA/SCL 再扫 | 是不是接反 |
| 6 | GPIO 直接给模块供电 | 3V3 脚位对不对 |
| 7 | **看实物照片** | 排针焊没焊、线插没插 |

第 7 步最不起眼，但本次就是靠它一击命中的。
