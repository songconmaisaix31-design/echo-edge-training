# 电脑提示联动与 30 分钟长跑（issue #6）

## 一、这一条为什么可以真做

issue #6 需要的是"电脑发提示 → 终端收 → 屏/播报/振动 → 回执"这条链路的**持续稳定性**。
它不依赖任何缺失的传感器：屏幕在线、TTS 在发帧、振动 GPIO 在翻转，电脑侧只有 USB 串口。

本轮真实 30 分钟数据来自本项测试。
屏幕和播报的实际效果由人工确认。脚本核对指令、触发和回执。

## 二、协议

| 方向 | 帧 | 说明 |
|---|---|---|
| 电脑 → 终端 | `HINT <n>` | n=1..8，指定提示语；`HINT <text>` 只上屏不播报 |
| 终端 → 电脑 | `ACK,<seq>` | 设备侧递增序号，收到一条回一条 |
| 终端 → 电脑 | `ENV,t,rh,p,tv,rv,pv,stamp,mock` | 每秒一条 |
| 终端 → 电脑 | `HR,bpm,q,valid,mock,stamp` | 每秒一条 |

`HINT` 的动作顺序固定：上屏 → 发 TTS 帧 → 振动 150ms（非阻塞）→ 回 `ACK`。
**ACK 在动作之后发**，所以"收到 ACK"意味着前面几步都执行过了，这比"发出去就算成功"有意义。

## 三、测量方法：为什么用设备时间戳

主机侧时间会被 USB 缓冲、驱动调度、Python GIL 干扰，用它算丢样会把主机的问题算到设备头上。

所以判据落在 `ENV` 行的 `stamp`（设备 `millis()`）：

- 相邻两行差 1000ms → 正常
- 差 2000ms → 中间少了 1 秒 → 记 1 个丢样秒
- 累加得到总丢样秒数，除以时长得到丢样率

`ACK` 用序号判缺号：序号是设备侧递增的，缺号说明某条提示没到（或被丢弃）。

重启用启动横幅 `==== EdgeTerminal` 的出现次数判断 —— **不能用"读不到数据"当重启**，
USB 掉线也会读不到，两者必须分开。

## 四、怎么跑

```bash
# 30 分钟正式跑
python firmware/tools/terminal_link_test.py --port COM4 --minutes 30 --hint-every 20

# 90 秒冒烟（改代码后先跑这个）
python firmware/tools/terminal_link_test.py --port COM4 --minutes 1.5 --hint-every 6
```

脚本会写一份 JSON 报告，含到达率、缺号数、丢样率、最大间隔、重启次数、脉率有效率。

## 五、结果

### 30 分钟正式跑（实机，COM4，每 20 秒一条提示）

```
时长              1800.1 s
提示 发送/到达    90 / 90   (到达率 100%, 缺号 0)
采样 实收/应得    1796 / 1800
丢样              0 秒 (0.0%)
相邻 ENV 最大间隔 1020 ms
脉率 行/有效      1796 / 100.0%
重启次数          0
格式错误行        0
串口收字节        403,366
```

四项核心指标：**提示全到达、零重启、零丢样、无格式错误。**

`1796 / 1800` 差的那 4 条是首尾各 2 秒的边界（预热与收尾截断），不是丢样 ——
丢样判定看的是相邻 `stamp` 增量，那里最大 1020ms，说明每秒都在，没有跳秒。

### 关于报告里那个 103.45%

第一次跑完后 `acks_received=90` 而 `hints_sent=87`，算出 103.45% 的到达率 —— 明显不可能。

**原因是脚本自身的计数 bug**：预热阶段发了 3 条提示，这 3 条的回执进了 `acks`，
但发送数被"预热不计入"的逻辑扣掉了。原始数据是对的（`ack_seq_first_last=[1,90]`、
`ack_missing=0`、90 个互不重复的序号），错的是分母。

已修：预热改成独立阶段，发完把统计整个清空，之后才开始计时。用 3 分钟复跑验证：

```
时长              180.2 s
提示 发送/到达    18 / 18   (到达率 100.0%, 缺号 0)
采样 实收/应得    180 / 180 (丢 0 秒)
重启次数          0
判定: 通过
```

这件事本身值得记一笔：**测量工具自己也会错**。103% 这种数一眼就该怀疑工具，
而不是去解释"为什么多收到 3 条"。判据里写着"到达率 100%"，超了就是 bug。

### 现场核对项（脚本无法覆盖）

跑的过程中屏上应该依次出现 8 条提示的英文标签（`IMG OK` / `ADJUST PROBE` /
`QUALITY LOW` / `CAPTURE DONE` / `HOLD STILL` / `PROBE READY` / `ATTENTION` /
`ENV READY`），每次同时下发一条中文播报帧。**这两件事要人眼/人耳确认。**

## 六、判定标准

| 指标 | 通过线 | 理由 |
|---|---|---|
| 提示到达率 | 100% | 提示是医生可见的操作指令，丢一条就是漏一次引导 |
| 重启次数 | 0 | 重启会丢传感器状态，30 分钟内不允许 |
| 丢样率 | ≤ 1% | 1Hz 采样下 30 分钟约 1800 条，1% 是 18 条；再多说明调度有问题 |
| 脉率有效率 | 仅记录 | 波形源是 mock，有效率反映的是算法收敛，不是真实灌注 |

## 七、已知不覆盖的部分

- **屏上文字是否清晰、播报是否听得清**：脚本看不见也听不见，需现场核对
- **振动是否真的震**：本批无马达
- **USB 物理层中断**（拔线、驱动重载）：脚本会表现为读不到数据，不会记为设备重启
- **长时间温漂**：终端在 USB 供电下连续跑，没有做温度记录

## 八、RTX 主机侧怎么接

实际部署时把 HINT 的产生换成模型输出即可，串口部分不变：

```python
import serial, time
ser = serial.Serial("COM4", 115200, timeout=0.2)

def hint(n):
    ser.write(b"HINT %d\r" % n)
    t0 = time.time()
    while time.time() - t0 < 1.0:                  # 等回执，最多 1 秒
        line = ser.readline().decode("utf-8", "replace").strip()
        if line.startswith("ACK,"):
            return int(line.split(",")[1])
    return None                                    # 超时要重发，不要静默丢
```

提示语义建议与影像质量判断绑定（清晰/位置偏/信号弱/完成），
不要发通用提示 —— 医生需要知道"现在该做什么"，不是"程序在跑"。
