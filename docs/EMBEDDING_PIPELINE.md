# 两阶段流程：冻结编码 + 轻量注意力头

把建模拆成两段：先让 PanEcho 把每个视频冻成一组向量，再在向量上训练一个很小的注意力头。这样做的直接好处是**换标签不用重新编码**——EF 复核协议里那 120 例一旦回来，重训只需要秒级，不用再等编码。

## 为什么这样分

| | 阶段一：编码 | 阶段二：训练头 |
| --- | --- | --- |
| 输入 | 原始视频 | `(n_clips, 768)` 数组 |
| 参数更新 | 无（完全冻结） | 只更新头，约 0.9 M |
| 成本 | 每视频数秒，一次性 | 全量一轮 < 1 秒 |
| 产物 | `work/emb/*.npy` | `runs/emb-head-*/best.pt` |
| 失败影响 | 编码器不合格 → 后面全白做 | 只影响当前标签与切分 |

编码器是外部资产（Yale CarDS 的 PanEcho），本仓库不训练也不分发它；阶段二才是我们自己的东西。这个边界让"换了基线"和"换了标签"都不会互相污染。

## 与 EchoFocus 的关系

结构同源：不做切面分类、把整段检查的所有片段当序列、Transformer 编码后池化、线性头回归。差别在三点：

1. **池化方式**：EchoFocus 用均值池化；这里用显式注意力池化，权重可以打印出来看它更关注哪些片段。
2. **训练数据**：EchoFocus 在本院数据上训练；这里用本仓库自己的标签重训，权重不共享。
3. **定位**：EchoFocus 作为外部方法对照出现在评估协议里，不作为参考标准，也不生成伪标签。

权重许可证为 CC BY-NC-SA 4.0，代码 AGPLv3；派生权重需同协议发布。详见 [ECHOFOCUS.md](ECHOFOCUS.md)。

## 成本实测

在本机（Windows x64、16 线程 CPU、无 GPU）上，PanEcho 编码一个视频：

| 每视频 clip 数 | 耗时 | 说明 |
| --- | ---: | --- |
| 8 | 约 4.3 秒 | CAMUS 这类 15–30 帧的短环足够 |
| 16 | 约 8–10 秒 | EchoFocus 的原设置，长视频才需要 |

按 8 clip 估算：EchoNet-Peds 的 7,643 段视频约 9 小时 CPU；同一批在 GPU 上通常压到 1 小时以内。因此**编码阶段应该在有 GPU 的机器上跑一次，产物随权重一起回传**，不要每次重跑。

## 数据边界

- 视频与嵌入都留在授权环境：`work/emb/` 与 `work/echo-index-private.json` 已被 `.gitignore` 排除。
- `index.json` 含 `subject`（患儿号），只能留在 `work/`；对外只发布聚合后的报告。
- PanEcho 权重从 Releases 之外的授权位置读取，通过 `--weights` 指向，不进仓库。

## 命令

阶段一（编码，可断点续跑）：

```powershell
$python = '.\.venv\Scripts\python.exe'
& $python -X utf8 .\embed_panecho.py `
  --weights '.\work\models\panecho.pt' --panecho-repo '.\work\PanEcho' `
  --video-dir '.\data\videos' --index '.\work\echo-index-private.json' `
  --out '.\work\emb' --clips 8 --report '.\runs\embed\summary.json'
```

`--index` 是可选的对照表，形如 `{"某文件.avi": {"subject": "P0001", "split": "train", "ef": 55.0}}`；阶段二要求每条嵌入都有 `subject` 与 `ef`，否则直接报错而不是默认分组。

阶段二（训练头 + 报告）：

```powershell
& $python -X utf8 .\train_emb_head.py `
  --emb '.\work\emb' --run-dir '.\runs\emb-head-v1' --epochs 200 `
  --report '.\runs\emb-head-v1\test.json'
```

报告包含样本量（按视频计）、MAE 口径（EF 百分点）、常数基线对照，以及 EF<50 的 AUROC 与阳性例数。按 [AGENTS.md](../AGENTS.md)，只有报告里的数字可以对外引用。

## 验证记录

在本机用公开 CAMUS（494 段视频 / 247 名病人，成人）跑通两阶段，非本仓库授权的儿童数据。目的不是给出性能结论，而是确认管线可用、并量出成本结构。

**阶段一（编码）**：494 段、每段 8 clip，平均 4.3 秒/段，单进程 CPU 共 35 分钟。产物 494 个 `.npy`，每个 8 × 768。

**阶段二（训练头）**：200 轮，78 秒。头参数 0.9 M，输入 `(8, 768)`。

官方测试集 100 段（50 名病人，未参与训练与选型）：

| | MAE（EF 百分点） | 偏差 | Pearson r | EF<50 AUROC |
| --- | ---: | ---: | ---: | ---: |
| 常数基线（训练均值 43.2） | 8.36 | −3.78 | — | 0.50 |
| **冻结 PanEcho + 注意力头** | **7.74** | −5.12 | **0.553** | **0.660** |

同一批数据、同一切分下，端到端从头训练的小骨干（MobileNetV4-conv-small，2.66 M，8 帧 @160px）为 MAE 11.87、r 0.048、AUROC 0.48——**不如常数基线**。两者差距不是调参问题，是"有没有可用的预训练表示"。

由此可以定下这条流程的定位：

- **它解决的是小数据下的表示问题，不是精度天花板。** r 0.55 说明信号真实存在，但 MAE 7.7 仍明显弱于本仓库在 Stanford 数据上的患儿级 MAE 3.80（见 [STANFORD_EF.md](STANFORD_EF.md)），两者数据与口径不同，不可直接比较，仅说明"这条路不是精度升级"。
- **偏差 −5.1 说明还没有校准。** 在验证集上拟合一个仿射校准即可消掉大部分，属于下一轮的低成本动作。
- **真正的收益是迭代速度。** 编码 35 分钟只做一次；此后换标签、换切分、换头结构都是分钟级，这正好接上 [EF 复测协议](EF_REVIEW_PROTOCOL.md)——120 例复核结果回来时可以立刻重训，不必重新编码。
